# Вход без почты и восстановление секретной фразой

## Важно
Это изменение требует не только загрузки HTML на Netlify, но и настройки серверной функции Supabase. Я не разворачивал её в вашем аккаунте. До выполнения шагов восстановление не работает, а сайт не позволит начать регистрацию без отключённого Confirm email.

Права модератора не меняются: владелец назначает их только через pedia_moderators в Supabase. Секрет восстановления прав модератора не выдаёт.

## 1. Подготовьте базу
В Supabase → SQL Editor создайте запрос, вставьте полный текст recovery-setup.sql и нажмите Run. forum-setup.sql должен быть выполнен ранее. Не отключайте RLS.

## 2. Разверните серверную функцию
1. Откройте Edge Functions в Supabase.
2. Выберите создание/развёртывание функции через редактор (Deploy a new function / Via Editor; названия могут отличаться).
3. Назовите функцию ТОЧНО account-recovery.
4. Замените пример в index.ts всем содержимым файла supabase/functions/account-recovery/index.ts из архива серверной настройки.
5. Разверните функцию.
6. В настройках этой функции отключите проверку JWT шлюзом (Verify JWT / Enforce JWT verification), если она включена. Это необходимо для восстановления без входа и нового publishable key. Сохранение секрета всё равно проверяет настоящий пользовательский токен внутри функции, а сброс проверяет секрет и лимиты.
7. При использовании CLI эквивалент — supabase functions deploy account-recovery --no-verify-jwt из проекта с supabase/config.toml.

Функция использует SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY и SUPABASE_ANON_KEY из стандартного окружения Supabase Edge Functions. Не копируйте значения этих серверных переменных в HTML, JavaScript сайта или чат. Если переменные отсутствуют в вашем окружении, настраивайте их только в серверных Secrets Supabase.

В Edge Functions → Secrets добавьте необязательную переменную ALLOWED_ORIGINS со значением https://craftnovarp.netlify.app. По умолчанию разрешён этот же адрес. Для другого домена замените значение; несколько адресов перечисляются через запятую. Не ставьте *.

## 3. Отключите подтверждение почты
В Authentication найдите настройки провайдера Email (часто Sign In / Providers → Email). Отключите Confirm email и сохраните. Сам провайдер Email оставьте включённым: он используется внутренне как механизм никнейм/пароль.

Пользователь НЕ вводит настоящий email. Сайт вычисляет технический адрес вида SHA256(никнейм)@accounts.novarp.invalid. Письма не отправляются, вход выполняется по никнейму. Технический адрес — не защита, а способ адаптировать Supabase Auth для никнеймов. Авторизация по-прежнему проверяется сервером.

Не отключайте RLS и не публикуйте service_role key. После отключения Confirm email регистрация по прямому API тоже не требует подтверждения — для публичного запуска нужны CAPTCHA и меры против спама.

## 4. Обновите сайт на Netlify
Загрузите все файлы из nova-rp-site.zip, сохранив подпапку vendor, и дождитесь публикации.

## 5. Проверьте обычным тестовым аккаунтом
1. Зарегистрируйте новый никнейм: 3–24 латинских буквы, цифры и _. Регистр букв при входе не учитывается.
2. Задайте пароль из 8 и более символов.
3. Для секрета нажмите «Сгенерировать»: получится случайный код из 128 бит энтропии. Запишите его вне сайта, например в менеджере паролей. Можно использовать фразу 16–200 символов, но короткие и распространённые слова небезопасны.
4. При успешной регистрации должно появиться сообщение о сохранении секрета. Если аккаунт создан, а секрет не сохранён — войдите и сохраните его через «Секрет восстановления» после устранения ошибки сервера.
5. Выйдите. Нажмите «Забыли пароль?», введите никнейм, сохранённый секрет и новый пароль.
6. Войдите с новым паролем.
7. Создайте НОВЫЙ секрет в настройках аккаунта. Старый одноразовый секрет после восстановления удаляется и повторно не работает.
8. Проверьте, что вход со старым паролем и восстановление со старым секретом не проходят.

Если вы потеряете и пароль, и секрет — восстановление только с помощью владельца проекта после проверки личности. Не обещайте пользователям восстановление без этих данных.

## Ранее созданные аккаунты
Они остаются доступны по прежней почте и паролю в том же поле «Никнейм». Войдите и задайте секрет в настройках аккаунта; для восстановления старого аккаунта указывайте его прежнюю почту. Автоматического переноса старого аккаунта на новый никнейм нет: не создавайте второй аккаунт вместо него, если нужно сохранить права и темы.

## Защита
- В базе хранится PBKDF2-SHA256-хеш с индивидуальной случайной солью и 210 000 итераций, а не открытый секрет.
- Сохранение/замена секрета требует текущего пароля и действительного JWT пользователя.
- Восстановление ограничено 5 попытками на аккаунт за 15 минут; есть дополнительный IP-лимит.
- Секрет одноразовый, потребляется атомарно; повторное использование запрещено.
- Из браузера нет доступа к таблицам секретов и лимитов.
- SQL rate limiter доступен только service_role.
- Секрет чувствителен к регистру; пробелы по краям убираются, применяется Unicode NFKC-нормализация.
- Для массового публичного запуска дополнительно нужны CAPTCHA, аудит и мониторинг. Часть кодовой базы ещё не проверялась end-to-end на вашем проекте.
- В редком случае ошибки изменения пароля после потребления секрета потребуется администратор. Не объявляйте этот механизм безусловной гарантией восстановления.
